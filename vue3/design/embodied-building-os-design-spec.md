# 具身建筑智能操作系统 UI/UX 设计规格

## 1. 产品定义

这不是一个安装了多个管理应用的桌面系统，而是建筑连接现实世界之后的操作界面。

建筑是主体：

- 空间是身体结构。
- 传感器是感官。
- 设备与执行器是器官和肢体。
- 事件是神经信号。
- 规则与策略是条件反射。
- 建筑智能体负责理解、推理、建议和编排。
- 人类操作员保留高风险动作的最终决策权。

核心交互闭环：

`感知 → 理解 → 决策 → 审核 → 执行 → 物理确认 → 留痕`

## 2. 当前界面的主要不足

### 2.1 首页没有表达建筑状态

桌面中心的大面积 Logo 只能表达品牌，不能回答以下问题：

- 建筑现在是否健康？
- 哪个空间正在异常？
- 哪些设备影响了人员和环境？
- 系统刚刚执行了什么？
- 执行结果是否真实发生？

### 2.2 信息架构以应用为中心

注册表、数据中心、设备中心和事件中枢把同一个物理对象拆散到了不同应用。操作员需要在模块之间切换，才能拼出一个空间或设备的完整上下文。

新的系统应以“站点 → 建筑 → 楼层 → 空间 → 设备 → 信号/事件/动作”为主关系，应用模块退居为能力入口。

### 2.3 空间只是文本字段

现有表格中的“位置”只是地址字符串，无法表达空间包含关系、邻接关系、影响范围和事件位置。具身建筑系统必须把空间变成第一类对象。

### 2.4 AI 没有成为可理解的系统能力

界面中缺少智能体的证据、推理、置信度、建议、权限边界和执行记录。只增加聊天窗口不能解决这个问题。

### 2.5 控制只到“指令已下发”

物理控制不能把接口成功当作操作成功。必须区分：

1. 指令已提交。
2. 网关已接收。
3. 设备已响应。
4. 传感器或状态回读已确认。
5. 超时、部分成功或回滚。

### 2.6 正常与异常的视觉权重接近

大量蓝色、渐变、卡片和图标同时出现，会降低异常信号的显著性。系统应“正常时安静，异常时明确”。

### 2.7 桌面窗口模型不完整

当前一次只支持一个 `activeApp`，最小化等同于关闭。它保留了桌面系统的外观，却没有提供窗口系统真正的状态连续性。

## 3. 新的信息架构

全局一级入口固定为：

1. **态势**：建筑整体状态、异常、智能体建议和运行闭环。
2. **空间**：建筑、楼层、区域及空间关系。
3. **智能体**：智能体能力、任务、建议、权限和执行记录。
4. **事件**：事件队列、关联证据、影响范围和处置过程。
5. **设备**：设备资产、状态、控制、维护和生命周期。
6. **数据**：实时信号、历史趋势、质量、血缘和订阅。
7. **系统**：驱动、注册、服务、资源和平台设置。

`注册表、资源管理器、驱动管理` 属于系统层，不应与日常运维入口拥有相同权重。

## 4. 态势首页结构

### 顶部命令栏

- 站点/建筑切换。
- 全局空间、设备和事件搜索。
- 建筑体征。
- 时间、告警和操作员身份。

### 建筑体征条

只保留能快速判断整体状态的四到六项指标：

- 在线设备。
- 空间舒适度。
- 今日能耗。
- 未处理事件。
- 运行中的智能体任务。

指标必须能下钻到对应空间和对象，不作为静态装饰卡片。

### 空间态势画布

- 建筑、楼层和空间是主视图。
- 环境、设备、能耗、人员和事件作为可切换图层。
- 事件与设备通过空间位置关联。
- 选中空间后，在原位置展开上下文，不强制跳转页面。
- 无三维模型时，先使用结构化二维楼层图，不能用无意义的伪 3D 替代。

### 建筑智能体面板

每条建议固定包含：

- 发现的问题。
- 证据和数据时间。
- 推理判断。
- 置信度与不确定性。
- 影响范围。
- 推荐动作。
- 是否需要人工审核。
- 执行后的验证条件。

### 运行轨迹

用连续轨迹表达：

`已感知 → 已分析 → 待审核 → 待执行 → 待确认`

已完成动作应展示物理回读证据，例如：

`照明关闭 → 设备响应 → 电流归零 → 已确认`

## 5. 控制交互规范

### 普通动作

低风险、可撤销动作可以直接执行，但必须提供执行中状态、回读确认和失败回滚。

### 高风险动作

门禁常开、批量断电、消防联动等动作必须展示：

- 精确作用对象。
- 空间影响范围。
- 持续时间。
- 风险说明。
- 当前操作者和权限。
- 二次确认或复核流程。

### 状态文案

禁止只使用“成功”。统一使用可验证状态：

- 指令已下发。
- 设备已响应。
- 状态已确认。
- 设备无响应。
- 状态与预期不一致。
- 已回滚。

## 6. 视觉语言

设计关键词：`安静、空间化、证据驱动、可执行、可信赖`。

### 色彩角色

- 页面背景：`#F3F6FA`
- 主表面：`#FFFFFF`
- 主文字：`#172033`
- 次级文字：`#667085`
- 分割线：`#E4EAF1`
- 主操作蓝：`#246BFD`
- 实时感知青：`#16B8C4`
- 已验证绿色：`#18A874`
- 风险橙色：`#F59E0B`
- 严重异常红色：`#E5484D`

正常状态不使用大面积绿色；绿色只表示已验证或恢复。红色和橙色不用于装饰。

### 密度与尺寸

- 采用 8px 间距基准。
- 主要点击目标不小于 44px。
- 正文建议 14–16px。
- 页面圆角 12–16px，避免每个区域都成为独立卡片。
- 阴影只表达浮层关系，普通内容使用边界和背景层级。

### 动效

- 传感数据变化使用 150–250ms 的状态过渡。
- 空间脉冲只用于新事件或实时选中对象。
- 执行过程用阶段推进，不使用无限旋转动画作为唯一反馈。
- 支持减少动态效果偏好。

## 7. 建议组件拆分

- `EmbodiedShell`：全局导航和命令栏。
- `BuildingVitalStrip`：建筑体征。
- `SpatialCanvas`：建筑/楼层/空间画布。
- `SpatialLayerControl`：环境、设备、能耗和事件图层。
- `EventSpatialAnchor`：事件与空间锚点。
- `BuildingAgentPanel`：证据、判断和建议。
- `ActionReviewCard`：人工审核与影响范围。
- `ExecutionTrace`：感知到确认的闭环轨迹。
- `EntityInspector`：空间、设备和事件的统一上下文面板。
- `ControlAction`：统一的控制状态机与风险确认。

## 8. 实施优先级

### P0：建立设计基础

- 统一颜色、字号、间距、圆角和状态语义。
- 建立控制动作状态机。
- 统一加载、空状态、错误和执行反馈。

### P1：重做态势首页

- 替换空 Logo 首页。
- 建筑体征条。
- 二维空间画布或真实楼层底图。
- 关键事件空间定位。

### P2：加入建筑智能体

- 证据、判断、置信度和建议。
- 审核与执行权限。
- 运行轨迹和审计记录。

### P3：重构设备控制

- 门禁、照明、监控等统一接入控制状态机。
- 将“接口成功”升级为“物理状态确认”。
- 支持超时、失败、部分成功和回滚。

### P4：收拢平台型应用

- 注册表、驱动和资源监控归入系统层。
- 数据中心从设备卡片目录升级为信号、趋势、质量和血缘视图。
